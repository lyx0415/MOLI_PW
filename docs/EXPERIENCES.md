# 多场景服务：运营与扩展说明

## 页面与使用路径

- 首页与主导航新增「场景探索」：`/experiences`。
- 六类专题页：`/experiences/esports`（线上电竞）、`offline-gaming`（线下电竞）、`fitness`（健身陪练）、`ktv`（KTV欢唱）、`boardgames`（桌游）、`chess`（棋牌）。
- 分类页展示场景介绍、参与建议、真实已上架服务和入驻/客服入口。没有服务时展示招募状态，不将未开通城市标记为可预约。
- 发现页支持服务方式、类别、城市、游戏、预算、收藏、接单状态筛选。类别、城市和预算必须同时匹配同一项服务，卡片价格与跳转默认选中的服务一致。
- 城市使用填写的名称精确匹配（不做自动定位）。运营审核时统一城市命名，例如「苏州」，不要同时使用「苏州市」。

## 陪玩、管理与客服

1. 新伙伴可直接选择线下类别申请入驻；管理员审核成年身份与技能资料后开通工作台，初始线下服务仍需单独审核。
2. 已入驻陪玩在「工作台 → 服务项目」选择场景，填写服务城市、公开营业场所、内容及额外费用说明。一个服务对应一个地点，多个地点分别创建服务。公开信息中不要填写私人住址或联系方式。
3. 线下服务每次保存都撤下旧展示并重新进入待审核。管理员在「线下服务审核」核对内容、场所、费用与所需资质，勾选实际核验后通过；可填写原因驳回或下架。陪玩能看到处理意见。
4. 审核使用版本号防止旧页面批准已修改内容。新预约也必须携带服务当前版本，信息变化后需要刷新确认。
5. 客户预约、付款、接单、履约、退款与评价沿用现有订单流程。线上与线下共用同一陪玩的档期，不能重叠；交通、准备和跨城安排仍需陪玩自行预留，系统尚不计算路程缓冲。
6. 下单时保存类别、方式、城市、场所、服务说明及额外费用说明；服务后续修改不覆盖已有订单。服务下架也不自动取消已约订单，运营者需协调履约或退款。
7. 关联订单的工单沟通页展示预约摘要及原始线下约定。客服只通过有权限访问的工单查看该摘要，不增加任意订单访问权限，也不返回私人联系方式或付款凭据。
8. 门店和活动合作暂由客服工单收集合作意向。已有审核、服务、档期、订单与售后可复用；尚无商户租户、多人拼团或场馆库存系统。

## 迁移与兼容

新增 `004-service-experiences.sql`：

- `moli_service_details` 保存类别、地点、费用与审核版本，按类别/城市/审核状态建立索引。
- `moli_order_experiences` 保存不可变的订单 JSON 快照。
- 不修改旧迁移、不改动旧站数据、不自动生成生产服务。没有扩展记录的既有服务继续按线上电竞解释；历史订单继续可读。
- 保存服务、审核和创建预约共用陪玩行锁，创建预约在拿到锁后重新读取服务状态与价格。
- API 保留原游戏列表；`/site.categories` 增加场景信息、已上架服务数与城市列表。`/providers` 新增 `category`、`mode`、`city` 参数。
- 线下下单新增必填语义字段 `serviceRevision`，取公开服务的 `revision`；旧线上调用无需变更。前后端必须一起升级。

升级前备份数据库，然后拉取 master、执行 `npm ci`、`npm run db:migrate`、`npm run build`，重启 API。部署过程避免旧前端与新 API 混用。不要在生产环境运行 demo seed。

## 演示与边界

全新开发演示库额外提供五个线下场景样例，明确标注虚构场所与演示服务；保留原六位游戏陪玩。对已经存在的演示陪玩不会自动追加样例，可通过工作台创建线下服务测试完整审核流程。

平台订单金额只包含页面列明的陪伴服务费；额外场地等消费按事前约定处理，未实现合并收款或场馆退款。当前不含地图定位、到场核销、紧急求助、职业资格自动认证、保险、团体人数库存、自动路程计算或商户分账。正式开展具体城市/场景前仍需完成真实人员、场所与所需资质核验，以及原有支付、邮件、HTTPS 等上线验收。
